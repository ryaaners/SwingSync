## Runtime decision

Use a separate Python 3.11 subproject with its own committed complete lock and virtual environment, outside the root uv workspace. Proposed direct pins: `mediapipe==1.2.2`, `numpy==2.2.5`, `opencv-contrib-python==4.12.0.88`, `av==16.0.1`. These are **metadata-compatible candidates**, not an empirically verified stack. Keep the root immutable ML lock/runtime intact even though the modern candidate has no direct NumPy constraint conflict. Run pose through an explicit separate interpreter/process; a root-process optional import cannot use a different environment safely. Do not silently replace OpenCV contrib with another distribution that owns the same `cv2` namespace.

The [current Python setup guide](https://developers.google.com/edge/mediapipe/solutions/setup_python) includes Python 3.11, Apple Silicon macOS and Linux x86_64/aarch64 with glibc ≥2.28. Actual wheel tags establish narrower release-specific support. The PyPI `Requires-Python` value is absent for all three inspected MediaPipe releases; that absence is not a compatibility guarantee.

## Adapter boundary

The [task documentation](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker?tab=Python) defines 33 anatomical landmarks, normalized image coordinates, hip-relative depth, separate world-coordinate outputs and visibility/presence. The [pinned Python result/landmark source](https://github.com/google-ai-edge/mediapipe/blob/2c2d4a7454d6358e0d6f0b54e254d231fe4cc78f/mediapipe/tasks/python/vision/pose_landmarker.py) and [container](https://github.com/google-ai-edge/mediapipe/blob/2c2d4a7454d6358e0d6f0b54e254d231fe4cc78f/mediapipe/tasks/python/components/containers/landmark.py) are the selected API authority. Container score fields can be absent (`None`), so do not fabricate confidence. Task-level presence/detection/tracking thresholds and per-landmark visibility/presence are distinct, uncalibrated model quantities.

Keep the existing `PoseSequence` interface: actual `float64[T]` decoded PTS seconds and `float64[T,33,4]` normalized image `(x,y,z,visibility)`, with width/height, explicit view, handedness and mirrored-coordinate flag. Preserve the full raw per-landmark presence array and frame status in a sidecar rather than silently changing four channels or overwriting visibility with presence. A documented presence filter can invalidate a point but must retain both raw scores and the filter policy. No extra sigmoid or clipping is justified merely by a generic container docstring; validate the pinned task outputs and suppress malformed/missing scores. Do not clamp out-of-frame x/y to create valid measurements. `z` stays unused; world coordinates, even when labeled meters upstream, do not establish calibrated 3D golf measurements.

Anatomical IDs remain fixed: nose 0, ears 7/8, shoulders 11/12, elbows 13/14, wrists 15/16, hips 23/24. Left/right refer to the subject's anatomy, not horizontal screen order. Require explicit golfer handedness; the adapter must not infer it from screen position or change IDs to match an expected swing. Lead/trail selection belongs to existing measurement logic.

Proposed conservative scope is an offline, bounded-memory CPU adapter and explicit artifact CLI, not serving/app integration. Accept decoded RGB frames with actual time metadata, call synchronous VIDEO mode once per frame in order, and close the landmarker reliably. LIVE_STREAM can drop input frames and is unsuitable for complete offline frame correspondence. IMAGE mode is a different, stateless extraction configuration; it must not be a silent fallback after VIDEO timestamp failure.

### Two clocks, one frame correspondence

The [official method reference](https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/vision/PoseLandmarker) and pinned source accept `detect_for_video(image, timestamp_ms: int, ...)` with increasing timestamps. An integer millisecond API clock is not decoded source PTS precision.

Proposed deterministic policy: retain integer decoder PTS and rational time base when available, plus unchanged float64 seconds. Store `origin_seconds = first_pts_seconds`; derive nonnegative relative times, then `api_ms = floor(1000 * (pts_seconds - origin_seconds) + 0.5)` (round half upward), recording the formula/version and full mapping. Validate finite/strictly increasing PTS, safe signed-int64 clock range, and strictly increasing API milliseconds **before inference**. Prefer exact rational arithmetic from decoder ticks for boundary rounding, with float64 seconds kept as the measurement coordinate. Reject duplicates/collisions/overflow; do not increment tied clocks, invent jitter, drop frames, resample, or reconstruct PTS as `api_ms/1000`. A distinct IMAGE-mode run may be explicitly requested/registered later.

For example, relative PTS `[0, 0.0004, 0.0011]` maps to `[0,0,1]` ms and must be refused under VIDEO policy even though actual PTS are strictly increasing. At 29.97 fps ordinary quantization varies clock increments; deriving `frame_index/fps` would erase actual VFR timing. Nearest-ms rounding has up to 0.5 ms mathematical quantization error before numerical effects; this is an API timing bound, not event/pose measurement accuracy. Measurement lookup continues to use actual observed PTS under the existing 1e-9-second software match tolerance, never rounded milliseconds. A 0.5 ms shift is far outside that match tolerance.

### Fail-closed observations and transforms

- Retain one row for every decoded frame. No pose produces NaN coordinates/visibility plus explicit `no_pose`; never carry forward or interpolate. Malformed lengths, nonfinite coordinates, absent scores, out-of-range scores and native exceptions get explicit failure/status, with no completed artifact published after a fatal extraction failure.
- Set `num_poses=2` for ambiguity screening and refuse frames returning multiple poses rather than selecting pose 0. The cap and detector misses mean a single returned pose is **not proof** of a single person in the scene. Require reviewed single-golfer input/identity continuity; unresolved identity or a suspected switch suppresses the sequence's spatial results. The API offers no established golfer identity guarantee for this use.
- Support only an explicitly defined upright raster convention initially. Record decoder display rotation/matrix, coded and display dimensions, sample/pixel aspect and all crop/resize operations. Reject unsupported nonzero/unknown rotation, non-square aspect or transform ambiguity until tested. Alternatively, implement one explicit upright pixel transform and verify coordinates/dimensions round-trip; do not apply both decoder and task rotations.
- Initially reject known mirrored source footage or unknown mirror convention for anatomical measurements. A documented display-only reflection of already inferred coordinates may set `PoseSequence.mirrored`; it changes x only and retains anatomical IDs. Running the model again on reflected pixels is a separate transformation and does not prove anatomical identity preservation. Never guess a left/right swap. Keep display rotation, mirror, golfer handedness and camera view as different provenance fields.
